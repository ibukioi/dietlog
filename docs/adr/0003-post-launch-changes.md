# ADR 0003: 公開後に変更したアーキテクチャ

- 日付: 2026-11-25
- 状態: 採用

本番公開(2026-11-23)の前後で、実際に使って分かった問題に合わせて設計書 v0.5 と ADR 0002 から次の点を変更した。設計書本文は v0.5 のまま残し、差分をここに記録する。

## 1. 本番環境の構成

| 項目 | 内容 |
|---|---|
| URL | https://dietlog-nine.vercel.app |
| アプリ | Vercel(Hobby)。Functions のリージョンは東京(`hnd1`)。Vercel のプロジェクト設定で指定している(`vercel.json` ではない) |
| DB | Turso `dietlog-prod`(AWS 東京 `ap-northeast-1`) |
| デプロイ | GitHub `ibukioi/dietlog` の `main` に push すると Vercel が自動でデプロイする。CI(GitHub Actions)は同じ push で並行して走る |
| 認証 | GitHub OAuth App(callback は `/api/auth/callback/github`) |
| Cron | `vercel.json` の 1 日 1 回(`/api/cron/cleanup`)。`CRON_SECRET` で保護 |
| 未設定 | Vercel Blob(`BLOB_READ_WRITE_TOKEN`)。商品写真の添付は無効 |

**判断**: DB とアプリを同じ東京に置き、1 リクエストで複数回 DB を読む画面の往復時間を抑える。Vercel の初期値(米国 `iad1`)のままだと、東京の Turso まで毎回太平洋を往復する。

## 2. 食品名の検索: 漢字・ひらがな・カタカナの表記ゆれ

**背景**: 成分表の食品名は「手羽さき」「にんじん」のように漢字とかなが混在し、「手羽先」で検索しても見つからなかった。

**判断**:

- 形態素解析ライブラリ kuromoji(0.1.2)で食品名の読み(ひらがな)を作り、`mext_food.search_reading` 列に保存する(マイグレーション `0002`)。シード時に作成し、既存の DB は `scripts/db/backfill-food-readings.ts` で埋める。
- 検索はまず表記どおりに探し、見つかった結果を先に並べる。そのあとに読みで見つかった結果を足す。
- 漢字の検索語で表記どおりの結果がある場合は、読みでは広げない(例: 「鮭」で「酒」が混ざらないようにする)。
- kuromoji が誤読する語は辞書で補正する(木綿→もめん、茄子→なす、長葱→ながねぎ など)。
- 「自分の商品」の絞り込みも同じ読みで照合する(`/api/search/reading`)。
- Open Food Facts は読みを理解しないので、結果が 0 件のときだけ、ひらがな・カタカナに変えて再検索する。

**トレードオフ**: kuromoji の辞書(約 17 MB)を、検索を使う Functions にだけ含める(`next.config.ts` の `outputFileTracingIncludes`)。1 つの Function は約 29 MB になる。ローカルでは辞書の初回読み込みに約 0.25 秒、プロセスのメモリは約 500 MB。読み込みは漢字を含む検索語のときだけ行う。

## 3. Open Food Facts の検索 API(ADR 0002 の 8 と設計書 §7.2 を変更)

**背景**: 設計書では旧検索 API(`cgi/search.pl`)を使い、アプリ全体で 3 回/分、503 を受けたら 60 秒止める設計だった。公開後、2 回目以降の検索がほぼ失敗した。

- 2026-11-24〜25 の実測で、旧検索 API は日本語・英語(nutella)を問わず 503 を返し続けた。商品の取得 API とトップページは正常だった。
- 新しい検索 API(search-a-licious)は日本語でも結果を返した(カップ麺 392 件、ポテトチップス 177 件、サラダチキン 110 件)。設計書の「日本語で当たらない」は、この時点では当てはまらなかった。
- 公式の上限は検索 10 回/分/IP。かな表記での再検索 1 回で、3 回/分の枠を使い切っていた。

**判断**:

- 新しい検索 API を優先し、失敗したときだけ旧検索 API を試す。栄養素のキーは同じなので、正規化の処理は共通にする。
- 新しい API はブランド名に言語の接頭辞(例: `xx:伊藤ハム`)が付くので外す。
- アプリ全体の外向き検索は 8 回/分(公式の 10 回/分に余裕を残す)。
- 両方の API が失敗したら 15 秒止める(サーキットブレーカー)。
- タイムアウトは 1 回 8 秒。東京からフランスの OFF まで往復するため。
- 失敗したときは、API 名・ステータス・所要時間を `[off]` で始まるログに残す。

**残るリスク**: Vercel の送信元 IP は他のサービスと共有している可能性があり、OFF 全体が混んでいるときは 503 が出る。そのときは手入力で記録できる。新しい API の結果には、熱量などが登録されていない商品も多い。これらは「不明」として表示し、0 にはしない。

## 4. ログイン・ログアウトの導線

**背景**: GitHub ログインの入口がお試しユーザーの設定画面にしかなく、ログアウトも設定画面の最下部にあった。トップページはログイン状態にかかわらず同じボタンを表示していた。

**判断**:

| 状態 | トップページのボタン |
|---|---|
| 未ログイン | 登録せずに試す / GitHub でログイン |
| お試し中 | 続きから使う / GitHub で本登録 |
| 本登録済み | 続きから使う / ログアウト |

- 本登録ユーザーは、すべての画面のヘッダーからログアウトできる。タブレット幅ではナビが折り返さないよう、アイコンだけを表示する。
- お試しユーザーにはログアウトを出さない。ログアウトするとお試しの記録に戻れなくなるため。やめるときは設定画面から削除する。

## 5. お試しから既存アカウントへの引き継ぎ

**背景**: お試し中に、すでに記録のある GitHub アカウントでログインすると、同じ日・同じ食事区分の `meal`、同じ日の `day_status`、同じ商品(`source` + `external_ref`)の一意制約に違反し、ログインに失敗する可能性があった。

**判断**: 引き継ぎ(`transferUserData`)で、重なる行は既存アカウントの行にまとめる。

- 食事: お試し側の明細を既存の `meal` に移し、空になったお試し側の `meal` を消す。
- 商品: 明細の参照先を既存の商品に付け替え、お試し側の商品を消す。
- 記録完了の印: 既存アカウントの値を残す。

**残る注意点**: お試しのサンプル記録(6 日分)も既存アカウントに移る。初めて試す人の記録を失わないことを優先した。
